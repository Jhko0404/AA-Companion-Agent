# 02. Companion Agent 평가 아키텍처 및 프롬프트 설계 베스트 프랙티스

본 문서는 엔터프라이즈 환경에서 **Companion Agent**의 조건부 코칭 카드(`Guidance instructions`), 글로벌 지침(`Model Guidance`), 그리고 콜 컨텍스트(`Inject context`)를 흔들림 없이 안정적으로 설계하기 위한 아키텍처 가이드입니다.

---

## 1. 턴바이턴(Turn-by-Turn) 모델 평가 구조 이해하기

### 1.1 매 대화 턴마다 AI 모델에 전달되는 6가지 프롬프트 구성 요소

Companion Agent는 등록된 Guidance 카드들을 하나씩 따로 평가하지 않고, **활성화된 모든 Guidance 카드를 단일 모델 요청으로 한꺼번에 평가**하여 현재 대화 상황에 가장 적합한 카드를 선택합니다. 매 턴마다 모델이 실제로 읽는 프롬프트는 다음 6가지 블록으로 구성됩니다:

```text
┌────────────────────────────────────────────────────────────────────────┐
│ 1. Built-in System Rules (사실성 유지, 마스킹 처리, 도구 호출 기본 규칙)  │
├────────────────────────────────────────────────────────────────────────┤
│ 2. Default Completion Criteria (각 Step의 완료 여부를 판단하는 기준)     │
├────────────────────────────────────────────────────────────────────────┤
│ 3. Model Guidance (글로벌 페르소나, 답변 어조, 500토큰 이하 공통 규칙)   │
├────────────────────────────────────────────────────────────────────────┤
│ 4. Enabled Guidance Instructions (카드별 Display name, Condition, Step)│
├────────────────────────────────────────────────────────────────────────┤
│ 5. Ingested Call Context (### 대문자_헤더 및 JSON 페이로드, 주입 시에만) │
├────────────────────────────────────────────────────────────────────────┤
│ 6. Live Transcript & Step History (최근 대화 내역 및 완료된 Step 기록)   │
└────────────────────────────────────────────────────────────────────────┘
```

### 1.2 4단계 내부 평가 루프 (The Four-Step Evaluation Loop)

트리거 이벤트(예: `Customer message`)가 발생할 때마다 모델은 내부적으로 다음 4단계를 순서대로 수행합니다:

1. **상황 파악 (`Situation`)**: 최근 대화 내역과 주입된 콜 컨텍스트(`### CUSTOMERCONTEXT` 등)를 요약합니다.
2. **조건 매칭 (`Matching_instructions`)**: 활성화된 모든 Guidance 카드의 `Condition*`을 대조하여 현재 턴에 부합하는 카드를 선택합니다.
3. **이전 단계 완료 판정 (`Completed_steps`)**: 이미 진행 중인 다단계 카드(`+ Add step` 사용)가 있다면, 이전 `Step*`이 대화록이나 도구 호출을 통해 완료되었는지 판정합니다.
4. **추천 생성 (`Next_action`)**: 아직 완료되지 않은 첫 번째 활성 `Step*`에 대해 도구 호출 또는 코칭 메시지를 생성하여 상담사 화면에 출력합니다.

## 2. 콘솔 입력 필드별 모델 가시성 (Field Visibility)

`Add guidance instruction` 팝업의 각 항목이 AI 모델에 전달되는지 여부를 정확히 이해해야 프롬프트 누락을 방지할 수 있습니다.

| 콘솔 UI 필드 | AI 모델 전달 여부 | 설계 시 핵심 주의사항 |
| :--- | :---: | :--- |
| **Display name\*** | ✅ 전달됨 | 상담사 화면의 카드 제목으로 그대로 노출되며, 다른 카드의 `Condition*`에서 상호 배타 조건을 걸 때 참조 이름으로 사용할 수 있습니다. |
| **Description (optional)** | ❌ **전달 안 됨** | 순수하게 관리자용 메모입니다. **AI 모델과 상담사 모두 볼 수 없으므로**, 여기에 발동 조건이나 도구 이름을 적어도 전혀 동작하지 않습니다. |
| **Instruction-level trigger (`Trigger*`)** | 시스템 사전 필터 | LLM이 호출되기 전에 플랫폼이 어느 발화자(`Customer message`, `Agent message`, `End of utterance`) 턴에서 평가할지 필터링합니다. |
| **Condition (`Condition*`)** | ✅ 전달됨 | 카드가 언제 활성화되어야 하는지 모델에게 설명하는 한 줄 조건문입니다. |
| **Actions (`Step*`)** | ✅ 전달됨 | 카드가 활성화되었을 때 호출할 도구와 상담사에게 보여줄 코칭 내용을 정의합니다. |

## 3. 채널별 설계 전략: 음성 콜(Voice) vs 디지털 채팅(Chat)

| 구분 | 음성 콜센터 (Voice / Telephony) | 디지털 채팅 (Digital Chat / Messaging) |
| :--- | :--- | :--- |
| **발화 특성** | 실시간 STT 변환으로 인해 문장이 짧게 나뉘어 들어올 수 있으며, 상담사가 통화 중 눈으로 긴 글을 읽기 어려움 | 고객이 완결된 문단 단위로 메시지를 전송하며, 상담사가 구조화된 텍스트나 표를 복사·활용하기 용이함 |
| **권장 트리거 전략** | 전체 트리거는 `End of utterance`를 사용하되, **고객 질문에 반응하는 일반 카드는 반드시 개별 트리거(`Trigger*`)를 `Customer message`로 설정** | 전체 트리거와 개별 트리거 모두 **`Customer message`** 권장 |
| **코칭 문구 길이** | 상담사가 즉시 소리 내어 읽을 수 있도록 **1~2문장 이내의 구어체**로 제한 | 불릿 포인트, 금액 비교 요약, 매뉴얼 조치 단계 등 구조화된 안내 가능 |

> [!WARNING]
> **음성 콜센터의 '첫인사 함정(Opening Utterance Trap)' 주의**:
> 음성 통화에서는 항상 상담사가 먼저 *"반갑습니다, 퓨어케어 고객센터 홍길동입니다. 무엇을 도와드릴까요?"*라고 첫인사를 건넵니다. 만약 카드의 트리거가 `End of utterance`로 되어 있고 조건문이 모호하면, 고객이 아직 아무 말도 하지 않았는데 상담사의 첫인사 직후에 카드가 발동할 수 있습니다. 따라서 고객 문의에 대응하는 카드는 **`Trigger*`를 `Customer message`로 지정**하는 것이 가장 안전합니다.

## 4. `Condition*` (발동 조건) 작성 3대 패턴

### 패턴 1: 대화 의도 기반 조건 (Conversational Intent)
- **권장 작성법**: *"누가(고객이) + 어떤 상황/의도를 말할 때"* 구조의 명확한 긍정문으로 작성합니다.
- **피해야 할 작성법**: 단순 키워드 나열(`"요금, 청구서, 인상"`)이나 부정문(`"단순 인사말일 때는 제외"`)은 LLM의 조건 매칭 정확도를 떨어뜨립니다.
- **좋은 예시**:
  ```text
  고객이 이번 달 렌탈 요금이 평소나 지난달보다 왜 더 많이 나왔는지 묻거나 전월 대비 청구 요금 차이와 인상 이유를 문의하는 경우
  ```

### 패턴 2: 콜 컨텍스트 주입이 보장될 때의 분기 (Guaranteed Context)
- IVR이나 CRM에서 전달된 `context_references` 데이터는 프롬프트 내에 `### 대문자_키이름`과 JSON 문자열로 삽입됩니다:
  ```text
  ### CUSTOMERCONTEXT
  {"customer_tier": "VIP", "ivr_authenticated": "true"}
  ```
- 컨텍스트가 항상 전달되는 환경에서는 대문자 헤더 이름과 정확한 JSON 키-값을 명시합니다:
  ```text
  CUSTOMERCONTEXT 섹션에 "ivr_authenticated": "true"가 포함되어 있고, 고객이 계정 청구 내역을 문의하는 경우
  ```

### 패턴 3: 콜 컨텍스트 누락/지연에 대비한 안전 분기 (Fail-Safe Default / Exception)
- 만약 네트워크 지연으로 인해 `CUSTOMERCONTEXT`가 아예 전달되지 않으면 프롬프트에 해당 섹션 자체가 생성되지 않습니다.
- 본인 확인이 필수인 업무에서는 **본인 확인을 수행하는 카드를 기본(`DEFAULT`)**으로 두고, **IVR 인증 완료 시 본인 확인을 생략하는 카드를 예외(`EXCEPTION`)**로 분리하여 서로의 카드 제목(`Display name`)을 교차 배제합니다:
  - **카드 A (`본인 확인 및 요금 조회 [DEFAULT]`) 조건**:
    ```text
    고객이 청구 요금을 문의하는 경우. 단, CUSTOMERCONTEXT에 "ivr_authenticated": "true"가 있어 '인증 고객 요금 즉시 조회 [EXCEPTION]' 카드가 적용되는 경우는 제외합니다.
    ```
  - **카드 B (`인증 고객 요금 즉시 조회 [EXCEPTION]`) 조건**:
    ```text
    고객이 청구 요금을 문의하고 CUSTOMERCONTEXT 섹션에 정확히 "ivr_authenticated": "true"가 존재하는 경우에만 적용합니다. 이 카드가 활성화되면 '본인 확인 및 요금 조회 [DEFAULT]' 카드를 대체합니다.
    ```

## 5. `Actions > Step*` 작성 및 분할 원칙 (The Checkpoint Rule)

### 5.1 체크포인트 규칙 (언제 `+ Add step`을 사용해야 하는가?)
- 각 `Step*`은 **대화록(Transcript)이나 도구 호출 이력(Tool Call)을 통해 '완료 여부'를 명확히 확인할 수 있는 독립된 턴(Turn)**이어야 합니다.
- **올바른 `+ Add step` 분할 예시 (당월 청구서 상세 조회 카드)**:
  - **1번째 `Step*`**: `get_invoice_breakdown(month="latest", line="")`을 호출해 전체 청구 금액과 보유 기기 끝자리(`048, 703, 843`)를 안내하고 어떤 기기를 상세 조회할지 질문합니다. *(상담사가 안내를 마치면 1번째 Step 완료)*
  - **2번째 `Step*`**: 고객이 특정 기기 끝자리(예: `"843"`)를 답하면 `get_invoice_breakdown(month="latest", line="843")`을 호출해 해당 기기 상세 내역을 안내합니다.

### 5.2 절대 별도의 `Step*`으로 분리하면 안 되는 항목
- *"고객에게 생년월일을 다시 묻지 마세요"* 같은 **부정 제약 조건**이나 *"표 형태로 정중하게 안내하세요"* 같은 **출력 스타일 지시**를 별도의 `Step*` 칸으로 분리하면 안 됩니다.
- AI 모델은 *"묻지 마세요"*라는 Step이 완료되었는지 대화록에서 증거를 찾을 수 없기 때문에 다음 Step으로 넘어가지 못하고 해당 Step에 영구히 머무르게 됩니다. 모든 제약 조건과 포맷 규칙은 반드시 **실제 행동 지시와 같은 `Step*` 입력칸 안**에 한 문장으로 결합하세요.

### 5.3 지식/매뉴얼 검색 도구의 무한 루프(Max Tool Loop) 방지 규칙
- 매뉴얼이나 문서를 검색하는 도구(`OpenAPI` 또는 `Data Store`)를 호출할 때, 고객이 질문한 두 가지 정보 중 하나(예: 필터 교환 방법)만 문서에 있고 다른 하나(예: 필터별 교환 주기 개월 수)가 문서에 없으면, LLM은 부족한 정보를 찾기 위해 검색어를 바꿔가며 **한 턴의 최대 허용 횟수(4회)**까지 도구를 반복 호출하다가 답변 텍스트를 생성하지 못하고 멈출 수 있습니다.
- **해결 원칙**:
  1. `Step*`과 `Model Guidance`에 **"매뉴얼 검색 도구는 턴당 딱 1회만 호출한 뒤 추가 재검색 없이 즉시 답변을 작성하세요"**라고 명시합니다.
  2. 문서 원본에 누락되어 있는 핵심 기준값(예: 필터별 권장 교환 주기 개월 수)은 지침 내에 직접 참고값으로 함께 기재합니다.
